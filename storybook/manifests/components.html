# DDR-000 : Qu’est-ce qu’un DDR

## Contexte

Le projet accumule depuis plusieurs années des couches de design et de pratiques de composition héritées (DSFR brut, design-system V1 sous DSFR, design-system V2, approche Tailwind seule, désormais shadcn également, code vitrine ad hoc). Les décisions qui ont structuré ces couches sont restées implicites : éparpillées dans des PR, des conversations, ou oubliées. Lorsqu’un nouveau composant ou une nouvelle page doit être conçue, l’absence de référent commun rend le choix de pattern coûteux et instable.

## Décision

Toute décision de design qui a un impact durable sur la composition, l’ergonomie ou la sémantique visuelle de l’application est consignée comme un **DDR (Design Decision Record)**, fichier Markdown versionné et publié dans un book afin d'être également accessible à tous les contributeurs.

Chaque DDR suit le format suivant :

- Frontmatter YAML : `title`, `created`, `status` (`proposé | accepté | déprécié | remplacé par DDR-XXX`).
- Sections obligatoires : **Contexte**, **Décision**
- Sections additionnelles possibles parmi : **Conséquences**, **Alternatives écartées**, etc.
- Nommage : `ddr-NNN-titre-court.md` (numérotation séquentielle, jamais réutilisée).
- Pas de préfixe d'espace : un DDR vitrine et un DDR transverse partagent la même séquence.

Les DDR sont la **mémoire décisionnelle** du design system. Ils ne décrivent pas l'existant, ni la progression de tâches ou migrations. Ils décrivent *ce que l'on applique à partir de maintenant et pourquoi*.

## Conséquences

- Une règle de design n'est opposable que si elle est portée par un DDR. À défaut, c'est une opinion individuelle, pas une doctrine du projet.
- Chaque DDR est exposé dans Storybook sous `DDR/`
- Une PR qui introduit un pattern de composition non couvert par un DDR existant produit soit un nouveau DDR, soit une révision d'un DDR existant.
- Une PR peut citer un DDR pour justifier un choix de pattern (`cf. DDR-001`).

## Frontière DDR ↔ ADR

- Un **ADR** couvre les arbitrages de stack, d'infrastructure, les choix techniques structurants, etc.
- Un **DDR** couvre un pattern d’interaction, une sémantique visuelle, de composition, etc.

## Ce qui mérite un DDR

- Un pattern d’interaction pour lequel plusieurs options valides existent.
- Une convention de composition avec des frontières non triviales.
- Une décision sémantique avec impact accessibilité ou cohérence multi-écrans.

## Ce qui ne mérite pas un DDR

- Une décision réversible sans coût (libellé d’un bouton, couleur précise d’un état).
- Un détail purement technique (nom d’une prop, type TypeScript).

# DDR-002 : Couches de composition du design system

## Contexte

L’application héberge aujourd’hui (en juin 2026) :

- du code **vitrine** sous DSFR global (≈ 260 composants dans `src/client/vitrine/**`) ;
- un **espace membre moderne** sous Tailwind v4 + shadcn (pages `src/app/(espace-membre)/espace-membre-v2/**`, shell `src/client/composants/espace-membre/*`, primitives `shadcn/components/ui/*`) ;
- un dossier `src/client/composants/design-system-V2/*` **legacy** (briques pré-shadcn d'un an, malgré le suffixe `V2`) ;
- du **legacy** espace membre V1 sous DSFR + styled-components.

Les frontières entre composant, composition et page sont implicites. Un même écran peut mélanger primitives shadcn, briques de `composants/espace-membre/*`, restes de `design-system-V2/`, sections métier et morceaux de pages historiques sans qu’il soit possible de dire à quelle couche chaque élément appartient. Cela rend le classement, la réutilisation et la migration coûteux.

## Décision

2. Le `Design system` est structuré en **4 couches de composition**, reprises strictement comme préfixes de titre dans Storybook et comme axe de navigation dans la documentation.

| Couche | Contenu | Exemples |
|---|---|---|
| Fondations | Tokens, palettes, typographie, iconographie, thématiques | Palette vitrine, échelle d’espacement V2 |
| Briques | Composants UI unitaires | `PageHeader`, `PageContent`, primitives `shadcn/components/ui/*` |
| Compositions | Assemblages de briques | `EspaceMembrePageShell`, `AppSidebar`, sections vitrine canoniques |
| Modèles de page | Pages complèteds, équivalents visuels d’une route | `Webapp/Page événements (exemple)` |

Chaque couche est susceptible d'être sous-divisées par **espace**, avec éventuellement des dossiers de composants partagés :

```
Briques
  ├─ Webapp/
  └─ Vitrine/

Compositions
   ├─ Webapp/
   └─ Vitrine/

Modèles de page
   ├─ Webapp/
   └─ Vitrine/
```

## Critères de montée d’une couche à la suivante

Les règles de classement ne dont pas rigides ou entièrement déterministes, il s'agit de faire preuve de bon sens, avec des heurisitiques comme :
- Un composant avec un slot nommé ou une API d’enfants typés est probablement une **composition**.
- Un composant qui consomme directement un type métier ou un store global est probablement une **composition**.
- Un composant qui assemble plusieurs compositions correspondant à une route ou un écran métier est certainement un **modèle de page**.

## Conséquences

- Chaque composant catalogué dans Storybook a un titre de la forme `Couche/Espace/Composant`.
- Un agent IA peut, à partir du chemin et du contenu du composant, proposer la couche d’appartenance correcte et signaler les ruptures de critères.

## Alternatives écartées

### Couches atomiques plus fines (atomes / molécules / organismes, etc.)

Le découpage en 4 couches (Fondations / Briques / Compositions / Modèles de page) est plus simple à appréhender et à appliquer que des sous-couches atomiques plus fines. Il est suffisamment granulaire pour différencier les niveaux de composition sans introduire de confusion ou de cas limites.

# DDR-004 : Scope de couleurs thématiques

## Contexte

Les **thématiques d'engagement** (Handicap, Emploi des jeunes, Transition écologique, etc.) portent chacune une identité visuelle (icône + deux couleurs) consommée par tout le produit.
La donnée vit côté CMS (Hygraph) et est exposée au code via `ThematiqueMapper` → `EtiquetteThematiqueReadModel` (`color1`, `color2`, `iconName`).

Trois patterns d'application visuelle coexistent ensuite dans le code :

1. **Tokens DSFR figés** (`bg-dsfr-orange-terre-battue-975`, `text-dsfr-green-emeraude-main-632`) : la couleur est gravée dans le composant.
2. **Injection `etiquette.color1` inline** (`style={{ backgroundColor: thematique.etiquette.color1 }}`) : data-driven, mais sans abstraction de rôle.
3. **CSS variables scopées** (`--thematique-main`, `--thematique-bg`) : pattern amorcé dans `ThematiqueCheckbox.tsx`, où un conteneur racine déclare les variables et les descendants peignent avec.

Côté Figma, un **plugin custom** parcourt les composants et réécrit le `fill` / `stroke` des calques dont le nom est préfixé par `@` (`@fill-main`, `@fill-950`, `@stroke-main`) avec les couleurs de la thématique sélectionnée.
Cette convention de nommage transforme un composant Figma en gabarit thématisable, et n'a pas d'équivalent formel côté code aujourd'hui.

## Décision

### 1. Convention de scope — CSS variables

L'identité d'une thématique est diffusée à un sous-arbre via des **CSS variables scopées** sur un conteneur racine.
Les descendants consomment ces variables sans connaître la thématique.

Rôles canoniques :

| Variable CSS | Usage | Alias par défaut |
|---|---|---|
| `--thematique-main` | Texte accentué, icône, bordure, accent | `etiquette.color1` |
| `--thematique-bg` | Fond clair (tag, panneau, en-tête de section) | `etiquette.color2` |
| `--thematique-stroke` | Trait / bordure | `--thematique-main` |
| `--thematique-on-bg` | Couleur de texte sur `bg` | `--thematique-main` |
| `--thematique-on-main` | Couleur de texte sur `main` | `background-default-grey` |

Pattern de consommation (les classes Tailwind v4 utilisent la forme courte `bg-(--var)`, imposée par le lint du dépôt) :

```tsx
<div
  style={{
    '--thematique-main': etiquette.color1,
    '--thematique-bg': etiquette.color2,
  } as React.CSSProperties}
  className="bg-(--thematique-bg) text-(--thematique-main) border-(--thematique-main)"
>
  {/* les descendants peignent avec les rôles, pas avec les hex */}
</div>
```

### 2. Parité Figma — convention `@fill-*` / `@stroke-*`

La convention de nommage des calques Figma (consommée par le plugin custom) est **alignée** sur les rôles CSS ci-dessus :

| Calque Figma | CSS variable | Sémantique |
|---|---|---|
| `@fill-main` | `--thematique-main` | Couleur principale de remplissage |
| `@fill-950` | `--thematique-bg` | Fond très clair |
| `@stroke-main` | `--thematique-stroke` (→ `--thematique-main`) | Bordure / trait |
| `@text-on-bg` | `--thematique-on-bg` | Texte posé sur `bg` |
| `@text-on-main` | `--thematique-on-main` | Texte posé sur `main` |

Tout nouveau suffixe Figma (`@fill-100`, `@stroke-dashed`, etc.) doit avoir un équivalent CSS var documenté ici **avant** d'être déployé dans le plugin.

### 3. Wrapper canonique : `ThematiqueScope`

Le composant `ThematiqueScope` formalise le pattern : il prend une étiquette `{ color1, color2 }` et pose les CSS vars `--thematique-*` sur son enfant.
Tout composant thématisable (`ThematiqueTag`, `ThematiqueCard`, `ThematiqueSidebarItem`, `ThematiqueCheckbox`) est consommé **à l'intérieur** d'un `ThematiqueScope`.

# DDR-011 : Zone « Candidats »

## Contexte

[DDR-001] organise le book en **deux** zones : `Design system` (stabilisé) et
`Explorations` (prospectif). À l'usage, un troisième état de maturité est apparu,
sans endroit où vivre : des sujets **sortis d'exploration**, validés dans leur
principe, mais **pas encore stabilisés** — leur décision de design est en voie
d'acceptation et/ou leur brique en voie de promotion.

Aujourd'hui ces sujets restent coincés sous `Explorations/` (ex. l'exploration
`Page shell & surfaces` empile six DDR candidats et leurs planches de spec), ce
qui brouille deux signaux opposés : « prototype jetable » et « en voie
d'intégration ». Un lecteur ne sait plus ce qui est encore une hypothèse de ce
qui est quasi-acquis et à raffiner.

## Décision

Le book comporte **trois** zones, du plus prospectif au plus stabilisé :

| Zone | Statut | Rôle |
|---|---|---|
| `Explorations` | Prospectif | Prototypes jetables, hypothèses confrontables (cf. [DDR-001]). |
| `Candidats` | En voie d'intégration | Sujets sortis d'exploration, validés dans le principe, à raffiner et/ou promouvoir. |
| `Design system` | Stabilisé | Doctrine et composants opposables (cf. [DDR-002]). |

La zone `Candidats` est un **sas** : tout ce qui s'y trouve a vocation à en
sortir, soit vers `Design system` (promotion), soit, en cas d'abandon, vers
`Explorations` ou la suppression.

### Convention de titre Storybook

Les entrées sont préfixées `Candidats/<sujet>/…`, par symétrie avec
`Design system/<couche>/…` et `Explorations/<sujet>/…`. La zone se range entre
`Design system` et `Explorations` dans le tri de la sidebar.

### Modèle de maturation (étages A / B / C)

Un sujet candidat se découpe en trois étages, repris de la roadmap de passation
de `Page shell & surfaces` :

| Étage | Nom | Livrable | Touche le code app ? |
|---|---|---|---|
| **A** | Arbitrage | `DDR candidat` → `DDR` `accepté` dans `stories/ddr/` | Non |
| **B** | Promotion | primitives sorties vers `Design system` (couche [DDR-002]), `!manifest` retiré | Non (DS) |
| **C** | Adoption | remplacement du legacy dans `src` | Oui |

### Critères d'entrée dans `Candidats`

- Le principe du sujet est **validé** (il ne s'agit plus de savoir *si*, mais
  *comment* l'intégrer).
- Un **DDR candidat** existe (ou est en cours), recensant les décisions ouvertes
  restantes.
- Le périmètre est **isolé** : un sujet = un sous-dossier `Candidats/<sujet>/`,
  pas un fourre-tout multi-scopes.

### Critères de sortie

- **Vers `Design system`** : DDR accepté (étage A fait) **et** brique stabilisée
  (étage B fait — style 100 % tokens, classée selon [DDR-002], `!manifest`
  retiré). L'adoption produit (étage C) peut suivre indépendamment.
- **Vers `Explorations` / suppression** : le sujet est abandonné ou rétrogradé au
  rang d'hypothèse.

## Conséquences

- `Explorations` redevient lisible comme couche **purement** prospective.
- Un sujet candidat ne re-décide rien dans une PR de code : un arbitrage qui
  rouvre repasse par un étage A (DDR), jamais dans l'adoption (cf. [DDR-000]).
- Un agent IA peut situer un sujet sur l'axe Explorations → Candidats → Design
  system et proposer l'étage de maturation manquant.
- [DDR-001] est **étendu** par le présent DDR (2 → 3 zones) ; il reste la base de
  l'organisation du book.

## Alternatives écartées

### Garder deux zones et un simple tag de maturité

Un tag (`!manifest`, `wip`…) sur des entrées restées sous `Explorations` ne sépare
pas visuellement les deux signaux (prototype jetable vs en voie d'intégration) et
laisse le fourre-tout multi-scopes perdurer. Une zone dédiée force l'isolement par
sujet et rend l'état de maturité lisible dans la navigation.

### Promouvoir directement vers `Design system`

Promouvoir sans sas obligerait à figer en une fois la décision (A), la brique (B)
et l'adoption (C). Le sas permet de **séquencer** ces étages à coûts et publics de
relecture distincts.

2. **Convergence en attente** — une galerie d'options candidate dont la décision
   n'est *pas encore tranchée* : ce n'est pas du déchet, c'est de la promotion en
   attente. On ne replie qu'**après** l'arbitrage.
3. **Dette technique** — un même composant dupliqué entre `kit-explo` et
   `socle-vitrine`, avec des imports encore branchés sur l'ancienne copie.

## Décision

### 1. Zone `Explorations/_archives/`

Le ménage **ne supprime pas** : il déplace. On introduit une branche
`Explorations/_archives/` (tag `!manifest`, hors navigation active) qui accueille
les explorations **supersédées** — celles dont un candidat reprend et dépasse la
matière. Le code reste lisible et réversible ; git conserve l'historique mais
n'est pas le seul filet.

Une exploration n'entre en archives que si **les trois** conditions tiennent :

- un **candidat (ou DDR)** reprend explicitement sa matière ;
- elle ne sert **plus de référence** d'écran (le candidat est plus abouti) ;
- **aucun import vivant** ne la tire (vérification graphe obligatoire — voir §4).

Les `.mdx` de **synthèse décisionnelle** (`Apercu`, `PartiRetenu`, `Analyse*`,
`Decisions*`, `Modele*`) ne sont **pas** archivés : leur valeur est documentaire,
pas exécutable. Ils restent comme trace du raisonnement.

### 2. Repli des galeries d'options (≠ archivage)

Une galerie `Options · …` candidate se replie **au moment où sa décision ouverte
est tranchée**, pas avant : on garde le parti retenu (câblé), on retire les
variantes confrontées. Tant que l'arbitrage est ouvert, la galerie **reste** —
c'est la matière de décision, sa présence est légitime.

### 3. Convention de statut

- **Fuite manifeste** : une story candidate qui n'a pas `!manifest` apparaît au
  manifeste comme stabilisée. Toute story sous `Candidats/` porte `!manifest`
  jusqu'à promotion explicite vers `Design system` (cf. [DDR-011], étage B).
- **Avancement de l'étage A** : un DDR candidat dont les décisions ouvertes sont
  mûres est passé en `accepté` dans `stories/ddr/` (numéro conservé), et non
  laissé indéfiniment en `candidat`.

# DDR-017 : Cycle de vie des présentations

> **Statut `proposé`.** Ce DDR fixe comment une présentation `nuxt-slides` qui
> embarque des écrans de Storybook **survit à l'archivage puis à la suppression**
> de ces écrans ([DDR-016]). Il devient opposable au passage en `accepté`.

## Contexte

Une présentation `nuxt-slides` peut embarquer des écrans Storybook par **iframe**.
Le couplage actuel (cf. `nuxt-slides/src/utils/storybook.ts`) est :

- le deck déclare en frontmatter `storybook: http://localhost:6007` ;
- chaque slide référence une story **par id** : `story="parti-retenu-accueil--page"`
  (annotation `:layout{story="…"}` ou composant `<StoryFrame story="…">`).

Conséquence : la présentation **dépend d'un Storybook qui tourne** et **casse dès
qu'un id de story bouge** (rename, déplacement vers `_archives/`, suppression). Le
couplage est *temporel* : la slide a besoin que la story existe au moment où on la
regarde. Tant qu'il subsiste, on ne peut **ni archiver ni supprimer** une
exploration sans casser les présentations qui la citent — exactement ce que
[DDR-016] cherche à débloquer.

## Décision

### 1. Une présentation diffusée est un livrable figé, pas une vue live

Le Storybook **vivant** sert le travail interne en cours. Dès qu'une présentation
doit **survivre indépendamment** des écrans qu'elle cite (diffusion externe,
archivage de l'exploration source), elle est **gelée** : on en produit un **bundle
HTML statique autoportant** qui embarque sa propre photo des écrans, servie à la
même origine (`/_storybook/`). Le bundle ne dépend plus de l'arborescence vivante.

L'infrastructure existe déjà : `nuxt-slides/scripts/bundle-standalone.js`
(`make bundle-standalone`). Elle copie un Storybook compilé dans le bundle, patche
le frontmatter `storybook:` vers le chemin relatif, et `nuxt generate` produit un
dossier déployable (GitHub Pages).

### 2. Bundle **réduit** aux écrans réellement cités

Le bundle de gel ne compile que les stories **référencées par le deck** :

1. **Extraire les ids** du `.md` : `story="([^"]+)"` (annotations `:layout{…}` +
   `<StoryFrame>`). Exemple vitrine : 6 ids distincts.
2. **Résoudre id → fichier source via `index.json`.** On lit l'index d'un build
   Storybook (la table autoritaire `id → importPath`), **pas** une re-dérivation
   du `title`. C'est crucial : les écrans vitrine épinglent un **`id` explicite**
   (`meta.id = 'parti-retenu-…'`) découplé du `title`
   (`Candidats/Home vitrine/L'accueil`) — voir §2.b. Re-slugifier le titre
   donnerait un id faux. Lire l'index rend en prime la **détection de référence
   cassée** gratuite (id absent ⇒ slide vide).
3. **Build Storybook filtré** sur les fichiers résolus. Storybook 10 construit par
   **glob de fichiers** (`stories`), pas par id : on restreint le glob aux
   `.stories.tsx` résolus. Vite suit ensuite le **graphe d'imports** (socle, data,
   kit) automatiquement — pas besoin de les énumérer.
4. **Bundler** ce mini-Storybook avec le deck via `bundle-standalone`.

> Outillé de bout en bout par **`make bundle-frozen BUNDLE_SLUG=<deck>`**
> (`nuxt-slides`) : résout les ids (`freeze-deck.js`), construit le Storybook
> réduit (`STORYBOOK_STORIES_GLOBS` dans `.storybook/main.ts`), puis enchaîne sur
> `bundle-standalone`. **Échoue avant tout build** si le deck référence une story
> absente. `make freeze-check` donne le rapport seul, sans rien construire.
> Pré-requis : un `index.json` issu d'un build complet (`make bundle-storybook`)
> pour la résolution. Validé sur `vitrine-t3-candidat-retenu` (bundle autoportant,
> Storybook réduit à 15 entrées, frontmatter patché vers `/_storybook`).

#### 2.a-bis. Deux pièges d'assets (surgis à la preuve visuelle)

Le rendu réel du bundle a révélé deux défauts **du flow `bundle-standalone`
lui-même** (pré-existants, pas introduits par le gel) :

1. **`staticDirs` du Storybook en URL racine.** Les écrans référencent leurs
   photos/fonts en absolu (`/vitrine/…`, `/fonts/…`). Dans le bundle ils vivent
   sous `/_storybook/`, donc l'iframe les demande à la racine du serveur → 404,
   écran « en alt-text ». **Correctif** : `scripts/mirror-storybook-assets.js`
   recopie les dossiers d'assets du Storybook à la **racine** du bundle (sans
   écraser les assets Nuxt), appelé par `bundle-standalone`.
2. **Base URL et URLs racine codées en dur.** Le deck Nuxt charge certains assets
   en absolu racine (`/themes/<t>.css`, `/backgrounds/…`, cf. `useTheme.ts`,
   `config/presentation.ts`) — **insensibles à `baseURL`**. Servir le bundle sous
   un sous-chemin (`/nuxt-slides/`) les casse. **Décision** : un bundle gelé se
   sert **à son origine** → `make bundle-frozen` bâtit en **base `/`**
   (`FROZEN_BASE_URL`). Le `/nuxt-slides/` reste réservé au déploiement GitHub
   Pages (`deploy-standalone`).

> `GET /api/_auth/session 404` au démarrage est **attendu** et bénin : route
> serveur sans backend en statique.

#### 2.a. Ce que le bundle réduit gagne — et ne gagne pas

Vérifié sur le cas vitrine (4 fichiers source, 6 ids) :

- **Surface** : l'index passe de ~105 fichiers / 296 entrées à **4 fichiers /
  15 entrées**. Le bundle ne navigue plus que les écrans du deck — fin de la
  confusion « écrans dépassés embarqués ».
- **Correction** : les 6 ids résolvent ; toute référence cassée est signalée
  **avant** gel (le script sort en code 2).
- **Poids : énorme, une fois l'élagage ajouté (révisé 2026-06-22).** Le gros du
  `storybook-static` (~95 Mo) vient des **assets statiques** : `staticDirs` =
  `apps/web/public` est copié **en bloc** (87 Mo, ~116 photos vitrine) quelle que
  soit la liste de stories. Or un deck réduit n'en référence qu'une fraction —
  l'atelier mécènes en utilise **0** (que des fontes, 800 Ko), la vitrine **12**
  photos. Le reste est du déchet pur. **Contrairement à l'hypothèse initiale,
  l'élagage est robuste et à très fort rendement** : on bâtit le Storybook réduit,
  puis on **scanne son JS/CSS bâti** pour les URL d'assets racine-absolues — après
  bundling, toute référence transitive (data files, kit partagé, `url()` CSS) est
  un littéral de chaîne, donc le scan attrape ce que le scan de source manque.
  - *Piège validé* : les chemins photos sont émis en **template literals**
    (` `/vitrine/…jpg` `) — le scanner doit inclure le backtick, sinon il
    supprimerait des assets utilisés (attrapé en validation sur la vitrine).
  - *Garde-fou* : `PRUNE_ASSETS=0` rebâtit avec le staticDir complet pour
    diagnostiquer un asset manquant.
  - *Résultat mesuré* : atelier **196 → 21 Mo**, vitrine **391 → 26 Mo** (ce
    dernier cumulait aussi le bug d'imbrication récursive, cf. ci-dessous). Le
    `_storybook` passe de 95 à ~9–14 Mo. Preuve de justesse : un asset référencé
    répond 200, un asset élagué répond 404.
  - *Outil* : `nuxt-slides/scripts/prune-storybook-assets.js`, câblé dans
    `make bundle-frozen` (défaut on). Override staticDir via `STORYBOOK_STATIC_DIR`
    dans `.storybook/main.ts`.

  Le gain de C est donc **la surface, la robustesse ET la taille**.

#### 2.a-ter. Le bundle ne doit pas embarquer Nuxt ni les autres bundles

Deux défauts d'architecture surgis à l'industrialisation du gel (révisé 2026-06-22) :

1. **Imbrication récursive + assets aspirés (résolu 2026-06-22).** `nuxt generate`
   copie tout `public/` dans sa sortie. Tant que l'hébergement et le mirror d'assets
   vivaient SOUS `public/` (`public/frozen/<alias>/`, `public/vitrine/`, `public/fonts/`),
   chaque nouveau bundle **aspirait les bundles déjà gelés ET leurs assets mirrorés**
   — d'où des photos *vitrine* retrouvées dans le bundle *atelier* (qui n'en
   référence aucune). `nitro.ignore` ne gouverne **que les routes**, pas la copie de
   `public/`. **Correctif en deux temps** :
   - **Sortir l'hébergement de `public/`** : les bundles vivent dans `.frozen/<alias>/`,
     le filet d'assets dans `.frozen-mirror/`, servis à l'origine par
     `nitro.publicAssets` (`nuxt.config`). `nuxt generate` ne les voit plus jamais.
   - **Rendre le bundle autoportant** : `scripts/rebase-storybook-assets.js` réécrit
     les URL root-absolues des stories (`/vitrine/x`, `/fonts/x`) en **relatif** dans
     le `_storybook` bâti, pour qu'elles résolvent DANS le bundle (`_storybook/<root>/`).
     ⚠️ **Piège du contexte de résolution** (attrapé à la preuve visuelle, 85 erreurs) :
     un `url()` CSS résout contre la **feuille** (`_storybook/assets/`) → préfixe `../` ;
     un littéral JS devenu `<img src>` résout contre le **document** (iframe.html à
     `_storybook/`) → **sans** préfixe. Le rebaser applique donc un préfixe **par type
     de fichier**. Le mirror `.frozen-mirror/` n'est plus qu'un filet future-proof
     (un consommateur non-rebasé), pas une dépendance.
2. **Nuxt-out : bundle Reveal-only (résolu 2026-06-22).** Le deck gelé était une app
   Vue hydratée (`<div id="__nuxt">`, `_payload.json`, Reveal monté au runtime). On
   embarquait un framework de **build** comme dépendance de **runtime**. Résolu **sans
   navigateur headless** — la voie idiomatique passe par le rendu Nuxt, pas un
   post-traitement :
   - **Retirer `<ClientOnly>`** autour du deck : il *tree-shake le contenu du build
     serveur*, donc tant qu'il est là le deck ne peut PAS se pré-rendre. Le deck est
     SSR-safe (tous les accès `window` sont en `onMounted`/`mounted`), sauf un piège :
     une **directive `.client`** (`v-french-typography`) n'existe pas au SSR →
     `ssrGetDirectiveProps` plante sur `getSSRProps` undefined. Fix : `getSSRProps(){}`
     + plugin universel (plus `.client`).
   - **`features.noScripts`** (gated mode bundle) → Nuxt **n'émet jamais** les scripts
     d'hydratation, `_payload`, modulepreload. À la source, pas de strip fragile.
   - **`features.inlineStyles: () => true`** → tout le CSS inliné en `<style>`
     (sinon le CSS scopé, chargé par le graphe JS qu'on retire, est orphelin → slides
     non stylées). On garde aussi les `_nuxt/*.css` (un import composable, `reveal.css`,
     échappe au predicate `.vue`).
   - **Plugin Nitro `render:html`** (`server/plugins/nuxtout-deck.ts`) : **ajout pur**
     (reveal.css/js + `Reveal.initialize` depuis `DEFAULT_REVEAL_CONFIG`) + réécriture
     d'**attributs d'URL** root-absolus → relatifs `../../` (le HTML est à
     `slides/<slug>/`, profondeur 2). ⚠️ Le rebase doit être keyé sur la **cible du
     chemin** (`/_storybook/`, `/vitrine/`…), PAS sur le nom d'attribut : sinon le
     lightbox Reveal `data-preview-link` échappe (bug attrapé : iframes 404 +
     X-Frame-Options deny). Reveal.js dist copié dans le bundle par le Makefile.
   - **CSS des composants MDC** : `inlineStyles` n'inline QUE les composants du sas
     SSR statique ; les slides sont rendues via le `<MDCRenderer>` dynamique, donc le
     CSS des composants MDC (`StoryFrame`, `SplitSlide`, `SlideContent`…) échappe à la
     collecte → leurs chunks `_nuxt/*.css` existent mais ne sont pas référencés. Fix :
     `scripts/link-deck-css.js` lie TOUS les `_nuxt/*.css` dans le HTML (le JS qui les
     chargeait est retiré). Sans ça, les iframes chargent mais s'effondrent (CSS de
     dimensionnement manquant).
   - **Scaled-iframe SANS JS (CSS-only)** : la vraie dépendance JS résiduelle du deck
     est `useScaledFrame` — un `ResizeObserver` mesure le pane, calcule `scale =
     largeur/1440` et pose `width/height/transform` inline. `noScripts` le supprime →
     l'inline `height:0px` figé au SSR reste → iframes effondrées. **Reproduit en CSS
     pur** via *container query units* : le pane devient `container-type:size`, l'iframe
     rend à `width:1440px` (logique desktop), et `transform:scale(calc(100cqw / 1440px))`
     — le truc clé est `cqw / 1440**px**` (longueur÷longueur = nombre, ce que `scale()`
     exige). La largeur du pane pilote le scale, **sans mesure JS**, auto-adaptatif à
     tout layout. Injecté par le plugin (mode bundle). Prouvé : 10 iframes 695px, viewport
     interne 1425px (fidélité desktop), remplit le pane. *NB lightbox : `data-preview-fit`
     (contain/cover/scale-down) règle le cadrage du media DANS l'overlay Reveal — piste
     d'amélioration source `StoryFrame.vue`, non incluse ici (touche aussi le live).*
   - **Résultat** : `_nuxt` 4 Mo de JS → **~270 Ko de CSS seul** (0 JS) ; deck HTML
     **100% autoportant Reveal** (0 réf Nuxt, `Reveal.isReady()`=true, 22 slides, 10
     iframes Storybook **rendues inline en zoom desktop**, **0 erreur console**). Bundle
     atelier **196 → 21 Mo**.

#### 2.b. Pré-requis : épingler l'`id` d'une story embarquée

Pour qu'un deck survive à la promotion d'un écran (exploration → candidat → DS),
la story doit porter un **`id` explicite stable** dans son `meta`, indépendant du
`title` (qui, lui, suit le rangement Storybook). C'est déjà le cas des écrans
vitrine (`id: 'parti-retenu-accueil'`). **Règle** : toute story susceptible d'être
embarquée par une présentation épingle son `id` ; déplacer/renommer la story ne
casse alors pas le deck.

> Garde-fou : si le build filtré casse un écran (dépendance non suivie), repli sûr
> sur le bundle complet (mécanisme A).

### 3. Déclencheur — par défaut, **gel à l'entrée en `_archives`**

Trois moments possibles de gel ; le **défaut retenu** est le premier, les deux
autres restent admis selon le cas :

La suppression définitive ultérieure ne casse plus rien. | Présentation **déjà diffusée** publiquement et exploration en voie d'archivage — **notre cas vitrine**. Découple tôt, sans surveillance. |

**deck ↔ stories citées** (`grep 'story="…"'` sur `presentations/`). Aucune
exploration n'est supprimée tant qu'un deck **non gelé** la cite encore.

# DDR-018 : Cycle de vie des présentations diffusées

> **Statut `proposé`.** Prolonge [DDR-017] (gel d'un deck) côté **diffusion** :
> comment un lien partagé reste **stable et accessible à vie** alors que sa source
> passe de *live collaboratif* (CodiMD) à *gelé* (bundle autoportant) puis
> *archivé*. Opposable au passage en `accepté`.

## Contexte

Une présentation traverse aujourd'hui trois états mal articulés :

| État | Où | Sert à | Lien Storybook |
| --- | --- | --- | --- |
| **Live** | note CodiMD (`md.…/<noteId>`) | éditer à plusieurs en séance | preview de PR / publié |
| **Repo** | `presentations/<statut>/<slug>.md` | versionner | `localhost:6007` |
| **Gelé** | bundle autoportant ([DDR-017]) | survivre sans Storybook live | `/_storybook` |

Frictions constatées :

1. **Réplication manuelle CodiMD ↔ repo** → forks et versions parallèles qui
   divergent.
2. **Le lien Storybook a trois valeurs** pour la même intention (local / preview /
   gelé), éditées à la main selon le contexte.
3. **Le lien diffusé pointe vers la source la plus volatile.** L'URL partagée
   (`/slides/codimd/<id>`) **re-fetche la note CodiMD à chaque visite**. Archiver
   la piste ou nettoyer la note **casse un lien déjà diffusé** — l'inverse de ce
   qu'on veut.
4. **`/slides/codimd/<id>` est long et opaque** (id CodiMD non lisible).

Le nœud : *un lien diffusé doit être le point le plus stable du système, or il
pointe vers le plus instable.*

## Ce qui existe déjà (à ne pas réinventer)

- Un stub repo peut déclarer `source: codimd` + `noteId:` : `/slides/<slug>`
  **récupère le corps CodiMD en live tout en gardant le frontmatter du repo**
  (lien Storybook, thème, contrôle d'accès). Cf.
  `server/api/presentations/[slug].get.ts`. Un slug repo *peut donc déjà* être une
  présentation live-collaborative.
- Les **dossiers de statut** (`public/draft/private/semi-private`) portent le
  **contrôle d'accès** — axe distinct du cycle de vie de contenu.

Il manque : un **axe de cycle de vie** (live → gelé → archivé) orthogonal à
l'accès, un **alias stable joli**, et leur résolution.

## Décision

### 1. Un registre versionné, source de vérité des alias

Un fichier unique `presentations/registry.yml` (versionné) mappe un **alias
stable** vers sa résolution. Exemple :

```yaml
# slug-joli → résolution
atelier-mecenes:
  title: Atelier mécènes — maquettes live
  lifecycle: frozen          # live | frozen | archived
  source: codimd             # provenance du corps quand live
  noteId: R90umc1HTWeLTAM9Ay90TA
  frozenBundle: atelier-mecenes        # dossier du bundle gelé (si frozen)
  storybook: pr-preview-1234           # alias Storybook (cf. §3)
  access: public
```

- **`lifecycle`** pilote *d'où vient le contenu* : `live` → fetch CodiMD ;
  `frozen` → sert le bundle autoportant ([DDR-017]) ; `archived` → idem gelé, mais
  retiré des listes (le lien reste résolu).
- **`access`** reste l'axe orthogonal (public/draft/…), inchangé.
- Le registre est **la** liste faisant foi ; les `.md` du repo deviennent des
  **stubs** (frontmatter + éventuel corps de repli), plus des répliques à
  maintenir à la main.

### 2. Un chemin court et stable : `/p/<alias>`

Nouvelle route **`/p/<alias>`** (plus court que `/slides/codimd/<id>`), résolue
**via le registre** :

- `lifecycle: live` → comportement actuel (fetch CodiMD), éditable en séance.
- `lifecycle: frozen|archived` → sert le **bundle gelé**, sans toucher CodiMD.

**L'URL ne change jamais** entre les états : `/p/atelier-mecenes` pointe vers le
live pendant la prépa, vers le gelé après diffusion. C'est l'alias stable
recherché. `/slides/codimd/<id>` et `/slides/<slug>` restent en **redirection**
vers `/p/<alias>` pour ne casser aucun lien déjà partagé.

### 3. Un alias Storybook unique (fin de la valeur en dur)

Le frontmatter ne porte plus une URL Storybook en dur mais un **alias** résolu
selon l'environnement, par une table du registre (ou `.env`) :

```yaml
storybookTargets:
  local: http://localhost:6007
  pr-preview-1234: https://storybook-pr-1234.…
  frozen: /_storybook         # injecté par le freeze
```

Un deck déclare `storybook: pr-preview-1234` ; en local on résout vers
`localhost:6007`, au gel vers `/_storybook` (déjà fait par [DDR-017]). **Une seule
intention, trois résolutions** — fin de l'édition manuelle.

### 4. Le freeze à la diffusion (rituel)

Quand une présentation passe de `live` à `frozen` :

1. **Rapatrier** le corps CodiMD dans le stub repo (commande `make pull-note
   BUNDLE_SLUG=<alias>` — fetch `/<noteId>/download`, écrit le `.md`). Fin de la
   réplication manuelle.
2. **Geler** via `make bundle-frozen` ([DDR-017]) → bundle autoportant.
3. **Basculer** `lifecycle: frozen` dans le registre. L'URL `/p/<alias>` sert
   désormais le gel ; le lien diffusé survit.
4. **Sort du live, au cas par cas** : la note CodiMD peut être conservée (lecture
   seule) ou archivée/supprimée — le champ `lifecycle` tranche par présentation,
   pas une règle globale.

### 5. Archivage côté repo

`lifecycle: archived` retire la présentation des **listes** (index, navigation)
mais **garde l'alias résolu** vers son bundle gelé. C'est l'équivalent decks de la
zone `_archives` des explorations ([DDR-016]) : on désencombre sans casser les
liens.

## Application aux deux cas réels

| Alias | CodiMD (noteId) | Stub repo | Cible | À faire |
| --- | --- | --- | --- | --- |
| `atelier-mecenes` | `R90umc1HTWeLTAM9Ay90TA` | `public/atelier-mecenes.md` | `frozen` | rapatrier + geler + bascule |
| `pistes-vitrine-t3` | `Jzryk3IHTS2UUqpMxaZMUg` | `public/pistes-vitrine-t3-2026.md` | à décider (`frozen` probable) | idem |

> ⚠️ Les deux liens **prod diffusés** fournis pointent vers la **même** URL
> (`…/slides/codimd/CXls8xC6-s`) — vraisemblablement un copier-coller. À lever
> avant migration : chaque alias doit résoudre vers **sa** note. Le registre rend
> cette collision visible (deux alias, deux `noteId`, une seule URL diffusée).

## Socle implémenté (2026-06-22)

- **Registre** `presentations/registry.yml` + `server/utils/registry.ts`.
- **Route stable** `/p/<alias>` (`src/pages/p/[alias].vue` + `server/api/p/[alias].get.ts`) :
  `live` → frontmatter du stub + corps CodiMD ; `frozen|archived` → redirige vers
  le bundle hébergé. **Édition manuelle du frontmatter du stub préservée** (lien
  Storybook par fichier conservé), comme demandé.
- **Convergence des chemins legacy** : middleware `alias-redirect.ts` 301 **tout**
  `/slides/<x>` qui résout à une entrée du registre — par alias canonique, par
  **slug du stub**, ou par chemin historique (`/slides/codimd/<id>`) — vers
  `/p/<alias>`. Garantit une **source de vérité unique** : `/slides/<slug>` ne peut
  plus servir une copie *différente* (stub brut, non gelée) de `/p/<alias>`. Les
  decks **hors registre** passent sans interception (200), la route canonique
  `/p/<alias>` n'est jamais touchée. *(Risque identifié : `/slides/<slug>` et
  `/p/<alias>` servaient deux contenus distincts — résolu.)*
- **Rapatriement** : `make pull-note` (CodiMD → stub, frontmatter préservé).
- **Champ `access`** : lève l'ambiguïté quand un même slug existe dans plusieurs
  dossiers (cas réel rencontré : `atelier-mecenes` en `public/` ET `semi-private/`).
- **Id épinglé** : la story embarquée porte `meta.id` stable (DDR-017 §2.b) — sans
  quoi un renommage de story casse le deck (cas réel : la story atelier avait été
  renumérotée `05-…` → `…-mai-2026`, les embeds du deck étaient cassés).

### Hébergement des bundles gelés — quick-win retenu

Le bundle gelé est copié sous **`.frozen/<alias>/`** (HORS `public/`, servi par
`nitro.publicAssets` à `/frozen/<alias>/`), via `make freeze-presentation`.
`/p/<alias>` redirige vers lui quand `lifecycle: frozen`. Simple, sans infra,
l'URL diffusée reste stable. *(Hors `public/` car `nuxt generate` aspire tout
`public/` → un bundle aspirerait les autres ; cf. [DDR-017] §2.a-ter.)*

### Provenance embarquée — le bundle est ré-engendrable seul

Chaque bundle gelé embarque un dossier **`source/`** (« au cas où ») pour rester
ré-engendrable et traçable sans le repo :

- **`<slug>.md`** — le markdown SOURCE fidèle au repo (frontmatter d'origine).
- **`<slug>--standalone.md`** — la variante patchée qui a *réellement* produit le
  bundle (`storybook: /frozen/<alias>/_storybook`).
- **`provenance.json`** — alias, slug, thème, date de gel, **commit git**.
- **`registry-entry.yml`** — l'entrée registre complète (noteId source, lifecycle…).

Ainsi, depuis le seul bundle diffusé, on sait d'où il vient, à quel commit, et on
peut le re-geler / re-diffuser à l'identique.

### Convergence des liens — côté CLIENT aussi (résolu 2026-06-22)

Le middleware `alias-redirect` est **serveur-only** : il converge `/slides/<slug>`
→ `/p/<alias>` au reload mais PAS en navigation SPA. Donc l'index ne doit pas lier
le legacy `/slides/<slug>` mais **directement `/p/<alias>`** : `/api/presentations`
expose désormais l'`alias` (depuis le registre), et la home lie `/p/<alias>` quand
présent (fallback `/slides/<slug>` hors-registre). Le middleware reste le filet
pour les liens externes déjà diffusés.

## Décisions ouvertes

- **Rapatriement & ids** : `pull-note` réécrit le corps depuis CodiMD ; si la note
  porte des ids de story périmés, le gel les ré-introduit. À terme : une **table de
  réécriture d'ids** au rapatriement, ou corriger la note source.
- **Push repo → CodiMD** : non implémenté (risque d'écraser une édition live).
- **Poids/versionnage** des bundles hébergés sous `public/frozen/` (commit vs
  hors-repo). Lié à [DDR-017].
- **Renommage de route** : `/p/` retenu ; alternatives `/d/`, `/v/`.

# DDR-019 : Feuille de route du socle design system

> **Statut `proposé`.** Boussole du chantier de fond : faire de la zone
> `Candidats` le socle solide d'un vrai design system pour un service à deux
> faces — **webapp sous auth** + **site vitrine**. Ce DDR pose la **doctrine de
> classement**, l'**inventaire cible**, la **cartographie des manques de
> fondation** et le **graphe de dépendances** adossé au planning produit. Il
> n'implémente rien : il oriente. Opposable au passage en `accepté`.

## Contexte

Le ménage des explorations est clos ([DDR-016]). Restait le cœur : les
`Candidats` ([DDR-011]) étaient un sas hétérogène, sans partition claire entre
ce qui sert la **webapp**, la **vitrine**, ou les **deux**. En parallèle, deux
composants vivaient en « Design system » sans être réellement câblés dans
l'application — un design system n'est crédible que si « stabilisé » veut dire
« utilisé en production ».

Trois constats ont structuré ce DDR :

1. **Le critère « câblé » n'était pas tenu.** `CarteContenu` et `ThematiqueScope`
   étaient documentés en Design system avec **zéro consommateur applicatif**.
2. **Le socle vitrine candidat est plus mûr que le webapp candidat** — l'inverse
   de l'intuition initiale. L'effort de structuration doit donc partir de la
   vitrine, qui porte les deux échéances les plus proches.
3. **Les fondations transverses sont implicites et disparates** — l'élévation au
   premier chef (tokens existants mais contournés partout), puis les surfaces
   greige, les rayons, les espacements.

## Décision

### 1. Doctrine de classement

- **Design system** = un composant n'y figure que s'il est **importé par au
  moins une page applicative live** (hors Storybook). Sinon il est `Candidat`.
- **`Candidats/{Partagé, Vitrine, Webapp}`** : trois zones.
  - **Partagé** : ce qui sert les deux faces — primitives (carte, badges) et
    doctrines transversales (états & messages).
  - **Vitrine** : site public (socle vitrine, home, référentiel, thématique, en
    savoir plus, palette vitrine).
  - **Webapp** : espace authentifié (collections, édition, parcours,
    embarquement, grammaire de surfaces).
- **Convention de nommage** : slug technique (dossiers, routes, ids) = `shared` ;
  label humain (titres Storybook) = **« Partagé »**.
- **Principes transversaux** : rangés **au cas par cas**, d'après ce que le
  sujet dit de lui-même. Exemple tranché : `grammaire-de-surfaces`, malgré une
  portée d'élévation transverse, est ancrée « espace membre » par son DDR-005 →
  classée **Webapp** (les faits priment sur la vocation prospective).

#### Rétrogradations actées

| Sujet | Avant | Après | Motif |
| --- | --- | --- | --- |
| Carte de contenu | `Design system/Briques/Partagé` | `Candidats/Partagé/Briques` | 0 consommateur applicatif |
| Thématiques | `Design system/Fondations` | `Candidats/Partagé/Fondations` | 0 consommateur (expose `thematique-scope`) |
| Palette vitrine | `Design system/Fondations` | `Candidats/Vitrine/Fondations` | sous-ensemble thématique vitrine |

> Le **code** de ces composants reste sa source dans `apps/web/src` (intouché) ;
> seule la **classification Storybook** change. La rétrogradation n'est pas un
> abandon : carte et `thematique-scope` sont au contraire **en tête de file de
> promotion** (cf. §4, chemin critique Home).

### 2. Inventaire cible (par zone × échelle)

Échelles : **fondations → briques → compositions → modèles de pages**.

**Partagé**

| Échelle | Sujet | Statut |
| --- | --- | --- |
| Fondations | Thématiques (référentiel + couleurs) | candidat mûr |
| Briques | Carte de contenu | candidat mûr, **à câbler** |
| Briques | Badges & étiquettes | candidat |
| Doctrine | États & messages (vides/erreurs/toasts) | candidat |

**Vitrine**

| Échelle | Sujet | Statut |
| --- | --- | --- |
| Fondations | Palette vitrine | candidat mûr |
| Briques | Section, Eyebrow heading, Grille colonnes, Bloc pédagogique | candidat mûr |
| Compositions | Panneau CTA, Gestes de composition, Sections canoniques | candidat mûr |
| Écrans | Home, Référentiel, Thématique (+ drawer), En savoir plus | candidat mûr |

**Webapp**

| Échelle | Sujet | Statut |
| --- | --- | --- |
| Fondations | Grammaire de surfaces (élévation, conteneurs) | candidat, **chrome ouvert** |
| Briques | (PageContent, PageHeader, Sidebar… déjà **stabilisés** en DS) | DS câblé |
| Écrans | Embarquement, Parcours, Collections, Édition | candidat |

#### 3.1 Élévation / ombres — *tranché (A1, 22/06/2026)*

> **Statut : décidé et gravé.** Anciennement l'enjeu phare (4 tokens
> `--shadow-carte*` froids, mono-couche, non documentés, contournés par ~25
> valeurs `shadow-[…]` ad hoc à 3 teintes mélangées). Arbitré par Lucas.

**Échelle canonique retenue** — 5 niveaux **nommés par rôle**, gravés dans
`apps/web/src/client/composants/tailwind.css` (`@theme`) :

| Rôle | Utilitaire | Token |
| --- | --- | --- |
| plate | *(aucun)* | `none` |
| repos | `shadow-repos` | `--shadow-repos` |
| survol | `shadow-survol` | `--shadow-survol` |
| flottant | `shadow-flottant` | `--shadow-flottant` |
| vedette | `shadow-vedette` | `--shadow-vedette` |

**Doctrine** (divergence assumée du DSFR, pour la chaleur) :

- **teinte unique chaude** `--ombre-teinte: 40 34 28` (taupe-greige), en
  remplacement du noir pur et des 3 teintes mélangées — accordée au greige des
  surfaces ;
- **2 ombres superposées par niveau** : *contact* (offset/blur courts, dense) +
  *ambiance* (offset/blur larges, diffuse) — une ombre simple « fait cheap » ;
- les anciens noms `--shadow-carte*` (jamais mergés sur `main`, introduits sur
  cette branche le 20/06) sont **renommés par rôle** : « carte » était trompeur,
  l'échelle sert aussi hero et drawer.

Fondation documentée : story **« Échelle d'ombres »** — spec d'intégration (table
de référence + à faire/à éviter + mises en situation). À articuler avec l'« échelle
d'élévation (5 rôles) » webapp de [DDR-005] — convergence, pas duplication.

**Ralliement** : les **écrans candidats vitrine** (Storybook) sont **ralliés** sur
les utilitaires (référentiel, thématique, panneau CTA + démos). Restent à traiter,
hors de ce passage : les `shadow-[…]` côté `apps/web/src` et la zone `webapp`, plus
le drawer latéral asymétrique `-16px 0 …` (à traiter comme **variante
directionnelle**).

#### 3.2 Surfaces / greige — *tranché (A2, 22/06/2026)*

> **Statut : décidé et gravé.** Recadrage clé : le greige n'est **pas une échelle
> de profondeur** (ce rôle est tenu par l'ombre, §3.1). C'est une **teinte de
> fond** qui ne parle qu'**en combinaison** — empilée sur elle-même, elle se
> neutralise.

**Décision.** Le **taupe léger** (undertone chaud R>G>B, accordé à
`--ombre-teinte`, volontairement très clair) devient le fond `greige` de
`SectionVitrine` et **remplace le gris froid `alt-grey`** dans le rôle
d'alternance neutre — plus clair, plus chaud, cohérent avec l'ombre. La grammaire
vitrine est donc : **`white` · `greige` · `alt-blue` · `blue`** (+ `thematique`
ponctuel). `alt-grey` est **retiré côté vitrine** mais reste valide en **classe
brute côté webapp** (page-shell, [DDR-005]).

| Token | Valeur | Utilitaire |
| --- | --- | --- |
| `--color-surface-greige` | `#faf8f3` | `bg-surface-greige` (fond de section) |
| `--color-surface-greige-carte` | `#f4efe7` | `bg-surface-greige-carte` (fond de carte) |

**Règle d'or** : jamais deux fonds de même famille superposés — section greige →
cartes blanches, section blanche → cartes greige ; l'**ombre** porte la
profondeur. La chaleur est subliminale, elle parle par *contraste*.

**Où c'est gravé.** Feuille **`tokens-candidats.css`** (Storybook-only, importée
par `stories.css` ; l'app charge `core.css`) — pas dans `tailwind.css` de prod,
tant que non câblé. Promotion = déplacer le token vers `tailwind.css`. Fondation
documentée : story **« Couleurs de fond & alternance »**.

**Ralliement fait.** Les constantes `*_GREIGE` de `gestes-vitrine.tsx` sont
devenues des **alias** des deux tokens (`CANVAS/SECTION_GREIGE → surface-greige`,
`DALLE_GREIGE* → surface-greige-carte`) ; les valeurs en dur `beige-gris-galet`
des écrans sont ralliées ; la **toolbar greige** (presets custom/dsfr) est
**retirée** (système `var(--greige-*)` mort). Recoupe la « gamme de conteneurs »
de [DDR-005].

> **Statut : décidé et rallié.** Deux gammes de gris de texte coexistaient : la

#### 3.5 Hairline (filet) — *tranché (audit du 22/06)*

> **Statut : décidé et rallié.** `ring-1 ring-black/5` (×20, + 2× `/6`) = un filet
> de séparation discret, identifiable mais non nommé.

**Décision.** Token `--color-filet` (→ `ring-filet` / `border-filet`), **accordé à
la chaleur** : `rgb(40 34 28 / 0.08)` — undertone taupe (`--ombre-teinte`) au lieu
du noir pur. Les 22 `ring-black/N` des candidats vitrine sont **ralliés** sur
`ring-filet` (à poser avec `ring-1`). `apps/web/src` intouché.

#### 3.6 Motion — *doctrine de retenue (audit du 22/06, sans token)*

> **Statut : doctrine documentée + nettoyage appliqué.** Tailwind v4 n'expose pas
> de namespace pour des durées nommées ; on documente la convention, le code reste
> idiomatique. **Principe : la motion sert, elle ne s'annonce pas.** Peu de
> transitions ; la profondeur (l'ombre A1) porte déjà le feedback.

**✅ Encouragé** (l'objet ne bouge pas) : ombre `repos→survol`
(`hover:shadow-survol`), couleur/bordure, translation d'un *indice* (flèche
`group-hover:translate-x-0.5`, opacité révélée).

**❌ Banni** (suggère une interactivité absente / trop voyant) : **zoom/`scale`
sur image**, **soulèvement `-translate-y` du bloc**, `transition-all`, durée
≥ 500ms sur du hover, parallax, entrées décoratives sur du texte.

**Nettoyage appliqué (22/06)** : 2 zooms photo (`scale`, `duration-500`) retirés,
7 soulèvements `-translate-y` retirés (carte/chip/bouton), `transition-[transform,
box-shadow]` ramené à `transition-shadow` quand seul le shadow anime, transitions
orphelines supprimées. Les flèches-indices (`group-hover:translate-x`) conservées.

| Durée | Rôle | Quand |
| --- | --- | --- |
| `duration-200` | rapide | hover (ombre, couleur, indice) |
| `duration-300` | standard | drawer, transition interne |
| `duration-500` | ample | **rare**, transitions non-hover seulement |

Story de référence : **« Motion (doctrine) »** (effets encouragés + contre-exemples).

### 6. Brique pivot : la carte de contenu

La carte est l'objet le plus dupliqué de la vitrine : chaque écran réinventait la
sienne. Doctrine : **une brique pivot couvre la plupart des cas**, on n'autorise
des cartes ad hoc que pour des registres qu'elle ne sait pas porter sans se
dénaturer.

**`CarteContenu`** (`@candidats/shared/briques/carte-contenu`) est cette brique.
Rapatriée du code applicatif (0 conso prod → candidat, cf. §1), elle est le
squelette versatile : c'est l'instanciation (slots + libellés) qui définit
l'usage. Axes :

- **Structure** : `orientation` (verticale / horizontale), `taille`
  (**`sm · md · lg`** — 3 registres ; l'usage réel n'en demande pas plus),
  `ratioImage`, `largeurImage`.
- **Lien** : `complet` (pied CTA) · `picto` (cliquable, flèche coin) · `bloc`
  (cliquable + libellé en pied) · `aucun`. `as="a"|"button"` : naviguer **ou**
  actionner (drawer/dialog) sans changer de page — un seul focusable.
- **Teinte** : `neutre` (blanc + filet) · `thematique` (voile `--thematique-bg`
  + accents `--thematique-main`, **pilotés par un `ThematiqueScope` parent** ;
  la carte est agnostique, elle lit les variables). La carte fusionne le `style`
  injecté par le scope (`asChild`) avec son voile — sinon `color-mix` est vide.

**Grammaire de contenu (slots typés par rôle — la forme dit le rôle, DDR-010).**
Une carte porte, au-delà de `titre` / `description` / CTA :

| Slot | Rôle | Primitive | Forme |
|---|---|---|---|
| `categorie` | catégorie / mot-clé (éditorial, stable) | **`Etiquette`** | pill, casse normale |
| `etat` | statut (système, varie dans le temps) | **`Badge`** | carré, MAJUSCULES |
| `meta` | donnée neutre (lieu, durée, **date**) | gris muted + picto | au-dessus du CTA |
| `medaillon` | picto d'accroche (cartes sans image) | en tête de corps | — |

Mémo **arrondi = catégorie, carré = état**. La **meta n'est jamais bleue** (le
bleu est réservé à l'interactif) ; une catégorie n'est PAS une meta (« Actualité »
= `categorie`, pas une ligne meta).

**Pas de `surtitre` / eyebrow.** L'ancien surtitre gris au-dessus du titre est
**supprimé** : il mélangeait dates (→ `meta`), catégories (→ `categorie`) et
numéros (souvent un doublon du titre). Chaque donnée a désormais un slot typé —
plus d'eyebrow ambigu.

**Emplacement des marqueurs** : `emplacementMarqueurs="start"` (défaut,
au-dessus du titre — zone `__start` du DSFR) ou `"image"` (par-dessus la photo).
`marqueurImage` reste un slot LIBRE pour une pastille posée sur l'image
(« Partout en France »), distinct des marqueurs typés.

- **Rythme vertical** calé sur le modèle DSFR (`fr-card__content`) : marges
  SÉMANTIQUES par relation, pas un `gap` uniforme. Marqueurs **détachés** du
  titre ; titre **aéré** de sa description ; meta **détachée** en bas, au-dessus
  du CTA. Ce qui VARIE par taille : titre, padding, rythme. Ce qui reste
  CONSTANT (lisibilité) : CTA, meta ; la description ne grandit qu'en `lg`.
- **Fondations ralliées** : `rounded-card` (§3.3), `ring-filet` (§3.5), ombre
  `shadow-repos → survol` au survol (§3.1), motion de retenue — ombre seule, pas
  de soulèvement (§3.6).

**Cartes ralliées** (registre canonique, à valeurs lissées) : cartes bénéfices
(médaillon), amorces home (médaillon + `bloc`/`actionPied`), cartes vedettes
référentiel (`thematique` + image/médaillon), cartes engagement
(`thematique` + `as="button"` → drawer).

**Exception assumée** : `CarteFamilleCompacte` (référentiel) — registre **liste
horizontale à pastille** (pastille picto à gauche + texte + flèche). Ni l'`image`
(zone pleine) ni le `medaillon` (en tête de corps) ne reproduisent la pastille
latérale ; la rallier dénaturerait la carte ou la brique. Laissée ad hoc, à
réévaluer si un slot « visuel latéral compact » émerge.

> **Garde-fou explorations/IA** : avant de créer une carte, vérifier que
> `CarteContenu` ne couvre pas le cas (teinte, médaillon, bouton, slots). Une
> carte ad hoc doit nommer le registre qu'elle ouvre — sinon, c'est une
> instanciation de la brique pivot.

## Usage via la brique `SectionVitrine`

Le rôle de fond est porté par la prop `fond` de `SectionVitrine`, qui résout la classe DSFR correspondante et impose le ton de texte adapté. Aucune classe `fr-*` structurelle n'est manipulée par le composant.

```tsx
import { SectionVitrine } from '@candidats/vitrine/socle-vitrine/briques/section-vitrine';
import { ThematiqueScope } from '@client/composants/shared/thematique-scope';

<main>
  <SectionVitrine fond="blue">Hero</SectionVitrine>
  <SectionVitrine fond="white">Contenu principal</SectionVitrine>
  <SectionVitrine fond="greige">Alternance neutre (chaude)</SectionVitrine>
  <SectionVitrine fond="alt-blue">Alternance identitaire</SectionVitrine>
  <ThematiqueScope etiquette={{ color1: t.color1, color2: t.color2 }}>
    <SectionVitrine fond="thematique" accent="var(--thematique-bg)">
      Section thématique « Jeunes » (ponctuelle)
    </SectionVitrine>
  </ThematiqueScope>
  <SectionVitrine fond="blue">Panneau CTA final</SectionVitrine>
</main>;
```
